# DeepSeek等待问题排查（4.3.1）

## 已确认的范围
报告涉及食物、账单和健康趋势三个请求类型。修复前工作区与已发布4.3.0 APK一致（SHA25632003bfd4e2c69d722d85785653c8ff12ab4097a61d3fc875ed418267ffe06d6）。共同原生传输文件从4.0.1到4.3.0相同；4.1至4.3的请求入口、WebView桥和交付令牌类也相同。未找到可将本次现象直接归因于4.3界面更新的证据。

旧传输设置连接20秒、读取空闲120秒，但没有整个请求的总时限。上传写入没有独立截止时间；持续收到少量数据也会延续读取，从而让用户长期看不到终态。

DeepSeek官方说明：非流式请求等待期间可能持续返回空行，尚未开始推理时服务端可能等待10分钟才关闭。这能解释为什么读取空闲超时不能作为整个请求的等待上限。官方资料：https://api-docs.deepseek.com/quick_start/rate_limit/ （2026-10-15核对）。这不证明某次真实等待一定由服务端排队引起；未使用用户密钥或私有内容重放。

## 验证方法
使用合成连接覆盖持续保活、上传/读取阻塞、取消、截止时间与迟到成功的竞争；使用模拟原生桥覆盖食物、账单、健康分析的终态与手动重试。测试不连接真实API，不产生调用费用。最终实现参数与完整结果见TEST-REPORT.md。

模型、官方端点、业务数据规则和发送授权不因本补丁改变。超时后不会自动再次付费请求；用户可核对后主动重试。实际设备网络、服务端排队和真实API调用尚未验证，不能承诺每次秒出。

## 可重复的旧版对比
运行bash tests/run-v431-wait-comparison.sh。测试保存已发布4.3原始传输代码，并与补丁分别编译：旧版在450毫秒合成观察窗口内持续收到空白仍未结束，阻塞上传也未结束；补丁测试使用180毫秒总时限/90毫秒上传时限，自动产生timeout终态。450毫秒不代表跑完生产120秒空闲超时；它验证可控路径，源码证明旧版没有整个请求/上传的截止机制。测试结束主动释放合成连接，无真实网络或费用。
